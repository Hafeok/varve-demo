# The demo script — specification

Version 0.1, filed by session 01 of #1, 2026-10-23. Proposed: the maintainer
accepts it with ADRs 0001–0008.

This is the product of the repository: seven steps a viewer watches, and an
evidence page CI generates. Each step says **what the viewer sees**, its
**acceptance criteria** (numbered, each one something CI checks with no human
in the loop), a **target time**, and the **name of its check**: the test method
that runs the step end to end. `docs/brief.md` is the authority; where this
page disagrees with it, the brief wins and this page is wrong.

**The targets are proposals.** They are set before anything is measured, so
they say what would convince a viewer, not what Varve already does. The
maintainer may change any of them at acceptance. A target that turns out to be
wrong changes by a pull request to this page that gives the measurement.

## The step table

The README carries an identical copy; `SpecTableGates` holds the two together.
`State` is `pending` (specified, not built), `passing` (its check exists under
`tests/` and CI runs it) or `withdrawn` (removed from the script, with the
reason recorded under the step). A step's state changes in the commit that
brings its evidence.

## Common rules

These hold for every step and for the evidence page. A check that cannot meet
one fails; it is never relaxed to pass.

- **C1 — Real runs only.** Every number, answer, chart and log line a viewer
  sees is produced by the run in front of them or by a CI run that is linked.
  Nothing is pre-recorded and presented as live. A replay says it is a replay,
  on screen.
- **C2 — Released Varve only.** Packages from nuget.org and the image
  `ghcr.io/hafeok/varve`, at the one pin in `Directory.Packages.props`
  (`VarveVersion`), the image verified by its attestation before use (ADR 0002).
- **C3 — Public API only.** The demo speaks to Varve through its HTTP protocol,
  its client and reader packages, and its documented command line. Never its
  internals, reflection, or a dataset's `derived/` files.
- **C4 — Always authenticated.** Every request carries an OIDC bearer token
  from the issuer in ADR 0007. No anonymous mode, in any form.
- **C5 — Reproducible from a pinned snapshot.** Every step runs from a snapshot
  pinned by hash (ADR 0008), so two runs of one commit give the same answers.
  The one exception is S4's live tail. Offline, S4 replays the snapshot's tail
  and labels it on screen as a replay.
- **C6 — A gap is shown, never worked around.** Where Varve lacks something a
  step needs, the step shows the gap with its Varve issue linked, and the issue
  carries a reproduction. "Varve issue to file" below marks one not yet filed.

### Facts about Varve the criteria rest on

Checked against Varve's repository at `v0.1.0-preview.11` on 2026-10-23. A bump
re-checks them.

- **F1.** Over HTTP a write request is **at most one commit**: none when its
  net effect is empty (Varve ADR 0094, ADR 0057).
- **F2.** Every response that touched a dataset carries `Varve-Position`, the
  head or the resolved as-of position, and an `ETag` (Varve ADRs 0094, 0096).
  Not every response does: `/health/*`, and problems written before a dataset
  is resolved (`401`, `403`, an unknown dataset, a malformed `Varve-As-Of`),
  carry `Varve-Request-Id` and no position.
- **F3.** As-of reads take `Varve-As-Of: position:<n>` or
  `Varve-As-Of: time:<RFC 3339>`. The time form resolves to the greatest
  position whose **Varve** commit timestamp is at or before it (ADR 0096).
  `Varve:Limits:MaxAsOfDistance` (default 10 000) bounds the commits an as-of
  read replays: the distance from the nearest checkpoint at or below the
  position, 0 at or below the newest checkpoint. Beyond it is
  `422 as-of-distance-exceeded`, whose `actual` member is the distance (Varve
  ADR 0114). The server takes no checkpoints by policy; an operator takes them
  on demand with `POST /manage/datasets/{name}/checkpoints`. A dataset's
  checkpoints are listed by `GET /manage/datasets/{name}/status`. Both need
  `admin` on the dataset (demo ADRs 0004, 0007).
- **F4.** The sequencer assigns commit timestamps as `max(clock, head's)`, and
  no request supplies one. Over HTTP the commit's cause is the server-minted
  request id, and no header sets it or any other commit metadata.
- **F5.** `GET /commits` takes a `pattern` filter (three N-Triples terms, each
  a term or `?name`) and resumes by position, exclusive (`from`, or
  `Last-Event-ID`). A request with no `to` streams history and then the
  present as one open range. A filtered-out commit is never a position the
  client holds, so resuming after the last position applied misses nothing
  (Varve's change-feed spec §4; source evidence in demo ADR 0009).
  `SparqlHttpClient.FollowAsync` has the same at-least-once, resumable
  contract, but its only filter is a graph.
- **F6.** A store refuses to open a log whose hash chain does not verify
  (Varve ADR 0014). Opening checks every segment, record and commit header
  against the chain, but checks record bodies against their hashes only above
  what `derived/` claims to hold (the newest checkpoint or persisted
  projection); a body below it is checked only when a later read needs it
  (Varve's `Log.cs`; citations in the traceability record of #1). No public
  command, API or route verifies the whole chain on demand.
- **F7.** Bulk load is one logical commit, embedded only (`varve load` over a
  directory, Varve ADR 0105), and records no agent; the server has no
  bulk-load endpoint. The demo does not use it: S1 is a full replay over HTTP
  (demo ADR 0008).

## S1 — Zero to query

**The viewer sees** one command, `docker compose up`, on a machine with only
Docker. The mock issuer starts, the Varve server starts, and the importer
authenticates and replays the snapshot over HTTP, one Varve commit per catalog
commit, printing commits per second and quads per second as it goes. It names
the snapshot's two parameters, N and the catalog time window, so the viewer
knows what history is loaded. The first answer to S2's question then prints,
with the time from the command to the answer.

**Acceptance criteria**

1. On a clean runner with only Docker, `docker compose up` with no other
   argument reaches a printed answer and exits the importer with code 0.
2. Every image the compose file starts is from `ghcr.io` or `public.ecr.aws`,
   pinned by digest; the Varve image's tag is `v$(VarveVersion)` and its
   attestation verifies (`gh attestation verify`) before the run.
3. The server runs with OIDC authentication against the mock issuer; a request
   without a token is `401`.
4. The load is a **full replay** (ADR 0008): every catalog commit the
   snapshot retains is sent as one SPARQL Update, authenticated as the
   importer, in catalog order. There is no bulk load and no base.
5. The load rate printed (commits/s and quads/s) is computed from the run's own
   wall clock and the counts the server acknowledged, and CI checks it equals
   the counts in the snapshot's manifest divided by the elapsed time printed,
   within rounding.
6. After the load, the importer's acknowledged commits number exactly the
   manifest's retained catalog commits, each acknowledged with its own
   `Varve-Position`, strictly increasing; every one carries the importer's
   agent; and `<urn:varve-demo:catalog-log>` holds one assertion per retained
   catalog commit.
7. The manifest states N (3 000) and the catalog time window, and the screen
   shows both. The window's lower bound is the one ADR 0008 records from the
   catalog; its upper bound is the snapshot date.
8. The time from `docker compose up` to the first answer, excluding image
   pulls (measured from the first container's start), is within the target.
   If it is not, the window is tuned, never N (ADR 0008); if no window that
   still holds S2's and S3's story meets it, the target changes here and in the
   README, with the measurement.

**Target:** ≤ 3 min. **Check:** `S1_ZeroToQuery`.

## S2 — Deprecated and vulnerable dependencies

**The viewer sees** a real `packages.lock.json` and one question asked of it:
*"Which of my dependencies, from a `packages.lock.json`, resolve to a deprecated
or vulnerable version, and what should I move to?"* The answer lists each such
package with its resolved version, the reason (deprecation reason or advisory
and severity), and the suggested version: the deprecation's alternate package,
or the lowest listed version above it with no known vulnerability. Packages
outside the demo's subset are listed as such, never dropped.

**Acceptance criteria**

1. The question runs as SPARQL over the protocol against the loaded snapshot,
   authenticated as the viewer role, and its query text is shown.
2. Every package in the lock file appears in the output exactly once, in one of
   three groups: *flagged*, *clean*, *outside the subset*.
3. CI compares the answer with an **independent reader** of the snapshot's
   catalog JSON, written with `System.Text.Json` and no Varve code, and the two
   agree on every package: group, reason, and suggested version.
4. The comparison runs over at least the committed demo lock file and a
   lock file CI generates with a known deprecated and a known vulnerable
   package from the subset.
5. Each query's response time, from request to last byte, is within the target,
   and the response's `Varve-Position` is the head printed by S1.

**Target:** ≤ 2 s per query. **Check:** `S2_DeprecatedAndVulnerableDependencies`.

## S3 — Time travel and diff

**The viewer sees** a slider over **catalog time** (ADR 0004). Moving it asks
S2's question as of that moment and shows a different answer: a vulnerability
not yet published, a version not yet deprecated. Every as-of answer shows the
catalog time asked for, the Varve position it resolved to, and that position's
Varve timestamp. It also shows where Varve started the read: "served from the
extents up to checkpoint `c`, no log replayed", or "`n` commits replayed after
checkpoint `c`". The viewer sees that time travel reads an index, not a
replay of the whole log. Then a diff between two positions: the quads
added and removed, grouped by package version.

**Acceptance criteria**

1. An as-of answer is read with `Varve-As-Of: position:<n>`, where `n` comes
   from the time index (ADR 0004), and its response's `Varve-Position` equals
   `n`.
2. The screen shows the catalog time asked for, the resolved position and that
   position's Varve timestamp; CI checks all three are present and that the
   timestamp is the one Varve reports for that position.
3. CI cross-checks the time index against Varve: for sampled catalog times, a
   binary search over as-of reads of `<urn:varve-demo:catalog-log>` finds the
   same position the index gives.
4. For at least one committed pair of catalog times, the as-of answers differ
   from each other and each equals the independent reader's answer over the
   catalog leaves up to that time.
5. Every as-of answer shows the checkpoint the read started from and the
   commits replayed after it, derived from the checkpoint list and Varve's
   rule (F3). CI checks the derivation against Varve: a request deliberately
   beyond the bound is refused with `422`, and its `actual` equals the distance
   the demo computes for that position.
6. `MaxAsOfDistance` is Varve's default; the dataset is checkpointed at least
   every `MaxAsOfDistance` commits during the import, so no position the
   slider offers is refused. Varve's server cannot be configured with a
   checkpoint policy (F3), so the importer takes the checkpoints with
   `POST /manage/datasets/{name}/checkpoints` through the operator client, as
   Varve's operator guide documents (ADR 0004). The screen says the importer
   takes them, as the operator, and why, with the Varve issue linked. When
   Varve ships a server-side policy, the importer stops. *Varve issue to file:
   "a checkpoint policy configurable on the server".*
7. The diff between two positions comes from Varve's diff over the protocol and
   equals the set difference of two as-of reads of the same graphs.
8. Because a details leaf replaces its version's graph (ADR 0008), a diff shows
   effective changes only: CI checks it holds no quad both added and removed.
9. Each as-of query and each diff is within the target.

**Target:** ≤ 2 s per as-of query or diff. **Check:** `S3_TimeTravelAndDiff`.

## S4 — Live change feed

**The viewer sees** a subscriber in one terminal and the importer in another.
As each catalog commit lands, the subscriber prints the package versions it
touched, with the position and the time from commit to print. When the viewer
kills the subscriber and restarts it, it resumes from its checkpoint, and any
commit delivered twice is printed again **marked as a repeat**: at-least-once
delivery is shown, not hidden (F5).

**Acceptance criteria**

1. The subscriber is `VarveDemo.PatternFeed`, this repository's own small
   client, labelled as ours on screen (ADR 0009). It subscribes to
   `GET /commits?pattern=…` as an open range, authenticated as the viewer
   role, and keeps its position in a file checkpoint saved after each commit
   is printed. The pattern is shown on screen.
2. Every commit the importer acknowledged during the run is printed by the
   subscriber, in position order, with no gap other than positions the viewer
   role cannot read.
3. CI kills the subscriber between a handler's return and its checkpoint's
   save, restarts it, and checks the redelivered commit is printed as a repeat
   and nothing is missing. It also kills the server mid-tail and restarts it;
   the subscriber reconnects and resumes, with the same two checks. Repeats
   are counted and the count is shown.
4. The latency printed, from the importer's acknowledgement to the print, is
   within the target for every commit, measured on one clock.
5. **Live** means a tail of the current catalog through the importer. Offline,
   or in CI, S4 replays the snapshot's tail at its original pace, and the
   screen says **REPLAY** on every line. CI runs the replay; the live mode is
   checked for starting and labelling only.
6. **The pattern is Varve's.** Every printed commit is one the server
   delivered under the pattern; the subscriber filters nothing itself. CI
   checks the printed changes equal the changes an independent reader of the
   snapshot finds matching the pattern, commit by commit.
7. Varve's own tests do not combine a pattern with resumption (ADR 0009). A
   commit this check finds missed or out of order is a Varve issue with the
   run as its reproduction, shown in S4, and never patched over in the client.

**Target:** ≤ 5 s from a commit landing to the subscriber printing it.
**Check:** `S4_LiveChangeFeed`.

## S5 — The same log in the browser

**The viewer sees** a static page that opens the same dataset's log in the
browser, in Varve's engine compiled to WebAssembly over OPFS, with the network
disconnected, and asks S2's question. The answer is identical to the server's,
byte for byte.

**This step is gated by ADR 0005.** It stays in the script only if the
measurement taken in slice 1 meets the thresholds there; otherwise it is
`withdrawn` with the numbers and a Varve issue.

**Acceptance criteria**

1. The page uses `Varve.Store.Browser` from nuget.org at `VarveVersion`, and
   opens a copy of the server's `log/` (never `derived/`).
2. In headless Chromium in CI, with the network disabled after load, S2's
   question returns results identical to the server's, compared as SPARQL
   results JSON after sorting.
3. A reload with the network disabled answers again (offline).
4. The payload, cold start and warm start are within ADR 0005's thresholds,
   and the numbers are on the evidence page.

**Target:** set by ADR 0005's measurement. **Check:** `S5_SameLogInTheBrowser`.

## S6 — Crash, restart, verify

**The viewer sees** a write loop against the server, each acknowledged commit's
position printed. Then `kill -9` on the server process, a restart, and two
results: the hash chain verifies, and every acknowledged commit is present. A
counter shows how many cycles have run. It repeats on demand.

**Acceptance criteria**

1. A writer sends single-commit updates, authenticated as the importer role,
   and records the `Varve-Position` of every acknowledged one (a `2xx` with a
   position). An update that was sent but not acknowledged is recorded as
   in doubt.
2. At a random moment the server's process is killed with `SIGKILL`, not
   stopped, and its container restarted on the same volume.
3. After the restart the server opens the dataset; a store whose chain does
   not verify refuses to open (F6), so an open is the verification the viewer
   can see today. The screen says exactly what that open checked: every
   header, and bodies only above the newest checkpoint. **Verifying the whole
   chain, bodies included, on demand** is a gap (F6): S6 shows it with its
   Varve issue linked. *Varve issue to file: "verify a dataset's hash chain on
   demand".*
4. Every acknowledged commit is present: the head is at or above the highest
   acknowledged position, and an as-of read at each acknowledged position finds
   that commit's quads. An in-doubt commit is reported as present or absent,
   never counted as lost.
5. CI runs at least 50 cycles per run, each within the target, and the counts
   (cycles, acknowledged commits, in-doubt, lost) go to the evidence page. Any
   lost acknowledged commit fails the run.

**Target:** ≤ 30 s per crash cycle, at least 50 cycles per CI run.
**Check:** `S6_CrashRestartVerify`.

## S7 — The database is files you can clone

**The viewer sees** `git clone` of a repository that holds a dataset's log, then
`git log` on it, one git commit per import batch, and then a Varve server
opened over the clone answering S2's question.

**Acceptance criteria**

1. The repository holds only the dataset's `log/` segments and a manifest; no
   `derived/` file is ever committed, and the server rebuilds its projection.
2. Copying the files is Varve's documented replica bootstrap (Varve ADR 0083);
   the clone is opened by the released server, unmodified.
3. `git log` shows the import history, and each git commit's message names the
   Varve positions it adds.
4. From `git clone` to the first answer is within the target, and the answer
   equals S2's at the same head.
5. Open, decided by an ADR in slice 3: how git stores the log's segments
   (append-only files diff poorly), and whether the repository is a release
   asset or a repository of its own.

**Target:** ≤ 1 min from `git clone` to an answer.
**Check:** `S7_DatabaseIsFilesYouCanClone`.

## E — The evidence page

**The viewer sees** one page, generated by CI from real runs, linked from the
README. Every number on it links to the CI run that produced it, with the
Varve version, the hardware, and the dataset.

**Acceptance criteria**

1. **Conformance.** The W3C SPARQL and RDF suites run against the released
   server through the protocol, by a harness in this repository, and the page
   shows passed, failed and skipped counts per suite. Varve's own published
   counts are shown beside them, labelled as Varve's.
2. **Differential.** S2's question, S3's as-of answers and a set of queries
   over the snapshot run against Varve and against Oxigraph (an image from
   `ghcr.io`, its ADR first) loaded with the same quads; the page shows the
   number of queries, agreements and every disagreement.
3. **Failure injection.** S6's counts from the run: cycles, acknowledged,
   in-doubt, lost.
4. **Benchmarks.** BenchmarkDotNet numbers for load, S2's query, an as-of read
   and a diff, with the hardware and the dataset stated.
5. **Not yet proven.** A list of what the demo does not show, including every
   open Varve issue the steps link and every `withdrawn` step with its reason.
6. The page is regenerated by every CI run on `main` and by every Varve bump,
   and states the run it came from. Nothing on it is edited by hand.

**Target:** regenerated by every CI run on `main` and every Varve bump, in
≤ 30 min of CI. **Check:** `E_EvidencePage`.
